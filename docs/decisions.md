## ADR-001: STT 기본 경로 — Web Speech API vs 로컬 Whisper

### 상황
두 문서 간 불일치가 있다.
- `ai-tech.md`: Web Speech API를 기본 STT로 사용
- `local-ai-architecture.md`: faster-whisper 로컬 서버를 권장

둘 다 장단이 있고, 어느 쪽을 기본 경로로 잡느냐에 따라 구현 순서와 의존성이 달라진다.

### 선택지

| | Web Speech API (브라우저 내장) | faster-whisper (로컬 서버) |
|---|---|---|
| **구현 비용** | 거의 0. 브라우저 API 호출만 하면 됨 | 서버에 모델 로드, 오디오 전송 파이프라인 필요 |
| **심사자 환경** | Chrome만 있으면 동작 | 심사자가 로컬 서버를 띄워야 하거나, 우리 서버에 접속해야 함 |
| **오프라인** | 불가. 인터넷 필요 (Google 서버 의존) | 가능. 완전 로컬 |
| **한국어 정확도** | 일상 대화는 괜찮으나, 게임 중 짧은 발화·배경음 환경은 미검증 | 모델 크기에 따라 조절 가능. 게임 발화에 맞춰 튜닝 여지 있음 |
| **interim result** | 지원. 말하는 중간에 텍스트가 올라옴 → 금기어 빠른 판정 가능 | 기본적으로 발화 종료 후 전사. 스트리밍 모드 구현 추가 비용 |
| **레이턴시** | 발화 → interim 200~500ms, final 1~2초 | 발화 → 전사 모델 크기에 따라 0.5~3초 |
| **비용** | 무료 (Google이 부담) | 무료 (로컬 GPU 사용) |
| **48GB 서버 부하** | 없음. 브라우저가 처리 | STT + LLM 동시 로드 시 메모리·GPU 경쟁 |
| **"무과금 로컬 AI" 서사** | 약함. 실제로는 Google 서버를 쓰는 것 | 강함. 진짜 로컬에서 다 돌린다는 기술적 어필 |

### 결정
**Web Speech API를 기본 경로로, faster-whisper를 향상 경로로 둔다.**

### 왜?

1인 개발, 7일 남은 상황에서 가장 중요한 건 **돌아가는 게임을 만드는 것**이다.

Web Speech API는 구현 비용이 거의 없고, interim result 덕분에 금기어 "빠른 경로"에 이상적이다. 심사자가 Chrome만 열면 바로 플레이할 수 있다는 것도 크다. faster-whisper를 기본으로 잡으면 오디오 스트리밍 파이프라인, 서버 모델 로드, 심사자 환경 대응까지 구현해야 하는데 이건 핵심 게임 루프가 아니다.

"무과금 로컬 AI" 서사가 약해지는 건 사실이다. 하지만 Web Speech API는 사용자 관점에서 무료이고, 금기어 판정 로직 자체는 서버에서 규칙 기반으로 돌아간다. AI 기술 문서에서 "STT 전사는 브라우저 내장 API를 활용하되, 금기어 판정·의도 추론·동료 행동은 모두 자체 로직"이라고 설명하면 된다.

faster-whisper는 시연 영상 촬영 시, 또는 본선(오프라인 48시간)에서 올리면 된다. 인터페이스만 동일하게 맞춰두면 전환은 쉽다.

### 트레이드오프 인식
- Web Speech API는 Google 의존이다. Google 서버가 느리면 게임이 느려진다.
- 오프라인 본선에서는 반드시 Whisper가 필요하다. 사전과제 이후 반드시 구현해야 한다.
- interim result의 정확도가 낮을 수 있다. 금기어 오탐이 잦으면 체감이 나빠진다.

### 리스크 완화
- 금기어 판정에 신뢰도 threshold를 둔다. interim에서 낮은 신뢰도면 final을 기다린다.
- STT 인터페이스를 추상화해서 Web Speech ↔ Whisper 전환이 설정 하나로 가능하게 한다.

## ADR-002: 형태소 분석기 — KoNLPy+Mecab vs kiwipiepy vs 정규식

### 상황
금기어 판정과 온보딩 명사 추출에 한국어 형태소 분석이 필요하다. 어떤 도구를 쓸지.

### 선택지

| | KoNLPy + Mecab | kiwipiepy | 정규식 + 자모 분리만 |
|---|---|---|---|
| **설치** | Java 런타임 + Mecab 사전 별도 설치. macOS에서 간혹 빌드 실패 | `pip install kiwipiepy` 한 줄. 순수 C++ 바인딩 | 외부 의존성 0 |
| **정확도** | 높음. 한국어 NLP 표준 | 높음. 최신 한국어 특화. 띄어쓰기 교정도 지원 | 금기어 3개 정도는 커버 가능하나, 활용형·합성어에 취약 |
| **속도** | 빠름 | 빠름 | 가장 빠름 |
| **Docker** | Java + Mecab 설치 레이어 추가 | pip만으로 완료 | 필요 없음 |
| **심사자 환경** | Docker 필수 | Docker 또는 pip | 아무것도 불필요 |

### 결정
**kiwipiepy를 기본으로, 정규식+자모를 1차 빠른 경로로 병용한다.**

### 왜?

KoNLPy+Mecab은 정확하지만 설치가 번거롭다. 1인 개발에서 환경 셋업에 시간 쓰는 건 낭비다. kiwipiepy는 `pip install` 한 줄이면 되고, 한국어 형태소 분석 성능도 Mecab과 대등하거나 더 낫다. 띄어쓰기 교정 기능은 STT 출력의 불완전한 띄어쓰기를 보정하는 데도 도움이 된다.

하지만 금기어 판정의 "빠른 경로"에서는 형태소 분석 없이 정규식+자모 분리만으로 먼저 판정한다. "열쇠"가 금기어일 때 transcript에 "열쇠"가 그대로 들어있으면 형태소 분석 없이 0ms에 판정 가능하다. 형태소 분석은 "열쇠를", "열쇠가" 같은 조사 결합이나 "열세" 같은 유사 발음을 잡을 때만 사용한다.

### 트레이드오프 인식
- kiwipiepy가 KoNLPy 대비 커뮤니티가 작다. 하지만 활발히 유지보수되고 있다.
- 정규식만으로 커버 안 되는 케이스가 분명 있다. 하지만 금기어가 3개뿐이고, 대부분 1~2음절 명사이므로 정규식의 커버리지가 생각보다 높다.

## ADR-003: AI 파트너 대화 — 대사 풀 vs 로컬 LLM vs 하이브리드

### 상황
AI 파트너가 플레이어의 우회 표현을 이해하고 행동하는 것이 게임의 핵심이다. 이걸 어떻게 구현할지가 전체 아키텍처에서 가장 어려운 결정이다.

### 선택지

| | 대사 풀 + FSM만 | 로컬 LLM 중심 | 하이브리드 (규칙→LLM 에스컬레이션) |
|---|---|---|---|
| **우회 표현 이해** | 못 함. 사전 정의된 상황에만 반응 | 가능. "반짝이는 작은 것" → 열쇠 추론 | 명확한 건 규칙으로, 애매한 건 LLM으로 |
| **레이턴시** | 0ms | 0.5~3초 | 명확할 때 0ms, 애매할 때 0.5~3초 |
| **구현 복잡도** | 낮음 | 중간. Ollama 연결 + 프롬프트 설계 | 높음. 두 경로 + 라우팅 로직 |
| **"AI 게임" 어필** | 약함. 스크립트 게임으로 보일 수 있음 | 강함. 진짜 AI가 이해한다 | 강함 + 안정적 |
| **실패 시 영향** | 없음 | 게임 멈춤 | 규칙으로 폴백 |

### 결정
**하이브리드를 목표로 하되, 대사 풀 FSM을 먼저 완성하고, 그 위에 LLM을 얹는다.**

### 왜?

이 게임의 핵심 어필은 "AI가 우회 표현을 이해한다"이다. 대사 풀만으로는 이걸 보여줄 수 없다. 그런데 LLM만 믿으면 실패했을 때 게임이 멈춘다.

구현 순서가 핵심이다:
1. 먼저 대사 풀 FSM으로 게임을 완성한다. 이 상태에서도 게임은 돌아간다.
2. 프롭 메타데이터(태그)를 풍부하게 설계한다. 이게 규칙 기반 추론의 품질을 결정한다.
3. 규칙 기반 점수가 애매할 때만 로컬 LLM을 호출하는 라우터를 추가한다.
4. LLM이 실패하면 대사 풀 FSM으로 폴백한다.

이렇게 하면 어느 시점에서 개발을 멈춰도 동작하는 게임이 있다.

### 프롭 메타데이터 설계가 관건

우회 표현을 규칙으로 해석하려면 프롭에 충분한 태그가 있어야 한다:

```json
{
  "id": "prop_key_01",
  "name": "열쇠",
  "zone": "storage",
  "tags": ["shiny", "small", "metal", "door-related", "holdable"],
  "descriptions": ["반짝이는", "작은", "문을 열 때 쓰는", "금속", "손에 쥘 수 있는"],
  "visual": { "color": "gold", "shape": "irregular", "emissive": true }
}
```

이 태그가 풍부할수록 LLM 없이도 "반짝이는 작은 것" → `prop_key_01` 매칭이 가능하다. LLM은 "문을 열 때 쓰는 것" 같은 기능적 설명을 해석할 때만 필요해진다.

### 트레이드오프 인식
- 하이브리드 구현은 두 시스템을 다 만들어야 하므로 공수가 크다.
- 하지만 대사 풀 FSM은 어차피 폴백으로 필요하니 버리는 작업이 아니다.
- 프롭 메타데이터 설계에 시간을 투자해야 한다. 이게 부실하면 규칙 기반도 LLM도 제대로 안 된다.

## ADR-004: 음성 입력 방식 — 상시 감지 vs Push-to-Talk

### 상황
기획서에서 미확정으로 남겨둔 항목이다. 게임 체감과 기술 구현 모두에 영향을 준다.

### 선택지

| | 상시 감지 (Always-on) | Push-to-Talk (PTT) |
|---|---|---|
| **몰입감** | 높음. 자연스럽게 말하면 됨 | 버튼을 눌러야 해서 약간의 단절 |
| **STT 비용/부하** | 계속 전사. Web Speech API는 무료이긴 하지만 끊김 가능 | 말할 때만 전사. 깔끔 |
| **금기어 오탐** | 높음. 혼잣말, 배경 소리, 한숨도 잡힐 수 있음 | 낮음. 의도된 발화만 판정 |
| **구현 복잡도** | VAD(음성 활동 감지) 필요. 발화 시작/끝 판단 어려움 | 버튼 누름/뗌이 명확한 구간 |
| **게임 디자인** | "말조심"의 긴장이 상시. 실수 발생 가능성 높음 | 버튼 누를 때만 긴장. 안전지대 존재 |
| **시연 영상** | 화면에 별도 표시 없이 자연스러움 | 버튼 누르는 행위가 보여야 함 |

### 결정
**Push-to-Talk을 기본으로 한다.**

### 왜?

상시 감지가 게임 디자인적으로 더 재미있을 수 있다. "아 열쇠... 아!!!" 같은 무의식적 실수가 게임의 백미일 수 있다.

하지만 1인 개발 MVP에서 상시 감지는 리스크가 너무 크다:
- Web Speech API의 상시 감지는 일정 시간 침묵 후 자동 중단된다. 이를 우회하려면 재시작 루프를 돌려야 한다.
- 배경음, 키보드 소리, 팬 소리가 전사되면 금기어 오탐이 발생한다.
- VAD를 직접 구현하거나 라이브러리를 붙여야 한다.

PTT는 이 모든 문제를 없앤다. 스페이스바를 누르고 있는 동안만 마이크가 열린다. 금기어 판정 구간이 명확하고, STT에 깨끗한 입력만 들어간다.

그리고 PTT에도 긴장감이 있다. "말해야 미션이 진행되는데, 말하면 얼 수 있다." 버튼을 누르는 순간부터 긴장이 시작된다. 이건 상시 감지의 "항상 긴장"과는 다른 종류의 재미인데, MVP로 검증하기에는 이쪽이 더 통제 가능하다.

### 트레이드오프 인식
- 상시 감지의 "무의식적 실수" 재미를 포기한다.
- PTT는 마이크 상태 UI를 반드시 보여줘야 한다 (녹음 중/대기 중).
- 향후 상시 감지 모드를 옵션으로 추가하는 것은 가능하다. PTT가 동작하면 상시 감지는 PTT의 상위 호환이므로 확장은 쉽다.

## ADR-005: AI 동료의 음성 출력 — TTS vs 자막 only

### 상황
AI 동료가 말할 때 실제 음성으로 출력할지, 텍스트 자막으로만 보여줄지.

### 선택지

| | 브라우저 TTS (Web Speech Synthesis) | 자막만 | 사전 녹음 음성 |
|---|---|---|---|
| **몰입감** | 중간. 기계음이지만 "말하는 느낌"은 있음 | 낮을 수 있으나, 게임 UI로 보완 가능 | 높음. 자연스러운 목소리 |
| **구현 비용** | 낮음. API 한 줄 | 가장 낮음 | 높음. 모든 대사를 녹음해야 함 |
| **레이턴시** | TTS 합성 시간 추가 (100~500ms) | 0ms. 즉시 표시 | 0ms. 파일 재생 |
| **동적 대사** | 가능. LLM이 생성한 대사도 읽을 수 있음 | 가능 | 불가. 사전 녹음분만 |
| **OS 의존성** | 목소리가 OS마다 다름. 일관성 없음 | 없음 | 없음 |
| **금기어 필터** | TTS가 금기어를 말할 수 있음. 필터 필요 | 텍스트 필터만 하면 됨 | 녹음 시 확인 |

### 결정
**자막을 기본으로, 핵심 대사(구조 "땡!", 경고)만 사전 녹음 효과음으로 보조한다.**

### 왜?

레이턴시가 핵심이다. AI 동료가 "그거 맞아!"라고 반응할 때 0.5초 TTS 합성을 기다리면 체감이 느려진다. 자막은 즉시 뜬다.

그리고 브라우저 TTS는 목소리가 OS마다 다르다. macOS에서 괜찮은 목소리가 Windows에서는 어색할 수 있다. 심사자 환경을 통제할 수 없으므로 TTS에 의존하면 안 된다.

대신 핵심 순간의 효과음은 사전 녹음한다:
- "땡!" (구조 성공)
- "조심!" (술래 접근 경고)
- "잡았다!" (술래 추격)
- 주문 합창 시 AI 동료 목소리

이 몇 개만 있으면 AI 동료가 "살아있는 느낌"은 충분히 전달된다. 나머지는 자막 + 이모트 애니메이션(점프, 고개 끄덕임, 물음표 이펙트)으로 대체한다.

### 트레이드오프 인식
- 시연 영상에서 AI가 "말하는" 장면이 없으면 임팩트가 줄 수 있다.
- 하지만 자막 + 효과음 + 캐릭터 리액션 애니메이션이면 영상에서도 충분히 보여줄 수 있다.
- LLM이 동적 대사를 생성하더라도 자막으로 보여주면 되니 기능 제한은 아니다.

## ADR-006: MVP 미션 구성 — T1 하나 vs T1 x3 반복 vs T1+T2+T3

### 상황
기획서에서 MVP는 "T1 미션 1개"로 정의했다. 하지만 미션 1개면 플레이 시간이 2분 이내로 짧아질 수 있다.

### 선택지

| | T1 미션 1개 | T1 미션 x3 (같은 메카닉, 다른 금기어) | T1 + T2 + T3 각 1개 |
|---|---|---|---|
| **구현 비용** | 최소 | 낮음. T1 로직 재사용, 프롭만 추가 | 높음. 3가지 메카닉 구현 |
| **플레이 시간** | ~2분 | ~4분 | ~5분 |
| **게임 볼륨** | 얇음. 핵심만 보여주고 끝 | 적당. 반복하면서 우회 표현의 재미가 쌓임 | 풍부. 다양한 AI 협동 경험 |
| **시연 영상** | 한 미션 장면만 | 비슷한 장면 반복으로 단조로울 수 있음 | 다양한 장면 확보 가능 |

### 결정
**T1 미션을 금기어 3개에 대해 3번 반복한다.** 시간이 남으면 T3를 1개 추가한다.

### 왜?

T1의 핵심("우회 표현으로 AI에게 프롭을 찾게 한다")이 이 게임의 얼굴이다. 이 메카닉을 3번 반복하면:
- 금기어가 바뀔 때마다 우회 표현이 달라지므로 반복이 지루하지 않다.
- 같은 코드로 3배의 플레이 볼륨을 만들 수 있다.
- 3개의 단서를 모아 최종 주문을 완성하는 흐름이 자연스럽다.

T2(동시 조작)는 타이밍 동기화 로직이 추가로 필요하고, AI 동료의 자율적 타이밍 맞추기가 구현 비용 대비 임팩트가 적다. T3(제한 설명)는 AI가 플레이어에게 설명하는 방향이라 T1의 변주로 보여줄 수 있어서 시간이 남으면 넣는다.

### 트레이드오프 인식
- T1만 3번이면 "이 게임 이것만 하나?" 느낌이 들 수 있다.
- 하지만 금기어가 매번 다르고, 프롭 배치가 바뀌고, 술래 압박이 점점 강해지면 반복감은 줄어든다.
- T3를 추가하면 "AI가 설명한다" ↔ "내가 AI에게 설명한다"의 역전이 생겨 다양성이 확보된다.

## ADR-007: 술래 AI — 단순 FSM vs AI 디렉터 통합

### 상황
기획서에 AI 디렉터가 술래의 속도, 반응 시간, 경로를 동적 조절한다고 되어 있다. MVP에서 어디까지 구현할지.

### 선택지

| | 고정 파라미터 FSM | AI 디렉터 통합 |
|---|---|---|
| **구현 비용** | 낮음. 상태 4개 + 고정 속도 | 중간. 긴장도 계산 + 파라미터 동적 조절 |
| **플레이 체감** | 예측 가능. 잘 튜닝하면 괜찮지만 일정한 패턴 | 매번 다른 느낌. "아슬아슬"이 보장됨 |
| **디버깅** | 쉬움. 행동이 결정적 | 약간 어려움. 왜 그렇게 움직였는지 추적 필요 |
| **기획 어필** | "FSM 술래"는 특별하지 않음 | "AI 디렉터가 극적 흐름을 조율한다"는 어필 포인트 |

### 결정
**고정 파라미터 FSM을 먼저 만들고, 디렉터는 파라미터 2~3개만 조절하는 얇은 레이어로 얹는다.**

### 왜?

AI 디렉터는 술래 FSM 위에 얹는 구조다. FSM이 먼저 완성되어야 디렉터를 올릴 수 있다. 그리고 디렉터의 핵심은 "술래 속도를 긴장도에 따라 조절한다"인데, 이건 코드 20줄이면 된다:

```python
seeker_speed = lerp(base_speed * 0.6, base_speed * 1.1, tension)
```

긴장도 계산도 `ai-tech.md`에 이미 공식이 있다. 복잡한 ML이 아니라 가중 합산이다. 이 정도면 FSM 완성 후 30분이면 붙일 수 있다.

풀 스펙 디렉터(구역별 함정 배치 타이밍, 이벤트 큐 관리 등)는 MVP에서는 필요 없다.

### 트레이드오프 인식
- 얇은 디렉터라도 "왜 술래가 갑자기 빨라졌지?"를 디버깅하려면 긴장도 값을 로그로 남겨야 한다.
- 하지만 이건 디렉터 없이 고정 속도로 튜닝하는 것보다 결과적으로 더 좋은 플레이 체감을 준다.

## ADR-008: 게임 상태 관리 — 서버 권위적 vs 클라이언트 권위적

### 상황
현재 아키텍처는 FastAPI가 Authoritative Game State를 관리하는 서버 권위적 구조다. MVP가 싱글 플레이어(인간 1명 + AI)인데, 서버를 굳이 분리할 필요가 있는지.

### 선택지

| | 서버 권위적 (FastAPI) | 클라이언트에서 전부 처리 | 하이브리드 |
|---|---|---|---|
| **구현 비용** | 높음. 클라이언트-서버 통신 전체 구현 | 낮음. 브라우저 하나에서 다 돌림 | 중간 |
| **심사자 환경** | 서버를 어딘가에 띄워야 함 | URL 하나로 끝 | 서버 있으면 서버, 없으면 로컬 |
| **멀티플레이 확장** | 이미 구조가 되어 있음 | 나중에 전면 재작성 | 확장 가능 |
| **AI 로직 위치** | 서버. Python 생태계 (KoNLPy, Ollama) | 브라우저. JS로 제한 | 선택 가능 |
| **본선 대비** | 본선에서 그대로 사용 가능 | 본선에서 재작성 필요 | 유연 |

### 결정
**서버 권위적 구조를 유지하되, Zero-Dependency Demo 모드에서는 클라이언트 단독 실행도 가능하게 한다.**

### 왜?

Python 생태계를 포기할 수 없다. kiwipiepy, Ollama, 프롭 검색 로직을 모두 JS로 포팅하면 시간 낭비다. 서버를 분리하면 Python으로 AI 로직을 편하게 짤 수 있다.

그리고 본선에서는 48시간 동안 현장 주제에 맞춰 새로 만들어야 한다. 서버-클라이언트 구조가 잡혀 있으면 본선에서 AI 로직만 교체하면 된다. 클라이언트에서 전부 처리하는 구조로 가면 본선에서 시간을 많이 잃는다.

Zero-Dependency Demo 모드는 심사자가 서버 없이도 게임을 체험할 수 있게 하는 것이다. 이 모드에서는 금기어가 고정이고, AI 파트너는 스크립트로 움직이고, 규칙 기반 판정만 JS로 돌린다. 게임의 "느낌"을 보여주는 데모 역할이다.

### 트레이드오프 인식
- 서버를 띄워야 한다는 건 심사자 입장에서 진입 장벽이다.
- Docker Compose로 원커맨드 실행을 보장하고, 동시에 Zero-Dependency 데모 URL도 제공한다.
- 두 모드를 다 만드는 건 공수가 추가되지만, Demo 모드는 AI 없이 고정 데이터로 돌리므로 복잡도가 낮다.

## ADR-009: 렌더링 — React Three Fiber(R3F) vs 순수 Three.js

### 상황
Three.js를 쓰기로 했는데, React Three Fiber로 감쌀지, 순수 Three.js로 갈지.

### 선택지

| | React Three Fiber (R3F) | 순수 Three.js |
|---|---|---|
| **React 통합** | 자연스러움. JSX로 3D 씬 작성 | 별도 관리. React 상태와 Three.js 동기화 직접 해야 함 |
| **학습 곡선** | R3F 자체의 패턴 학습 필요 | Three.js 공식 문서 그대로 |
| **UI 혼합** | React DOM UI + 3D 씬이 한 트리 | HTML overlay + canvas 분리 |
| **성능** | 약간의 오버헤드 | 직접 제어로 최적화 여지 |
| **생태계** | drei(헬퍼), rapier(물리) 등 R3F 생태계 | Three.js 예제 풍부 |
| **코드량** | 적음. 선언적 | 많음. 명령적 |

### 결정
**미확정. 첫 씬을 양쪽으로 30분씩 프로토타이핑한 뒤 결정한다.**

### 현재 기울어지는 방향
R3F 쪽으로 기울어져 있다. 이유:
- UI(HUD, 자막, 금기어 표시)가 많은 게임이라 React DOM과 3D의 혼합이 빈번하다.
- drei의 `Text`, `Html`, `OrbitControls` 등이 즉시 사용 가능하다.
- Zustand와의 통합이 자연스럽다.

하지만 R3F에 익숙하지 않다면 순수 Three.js가 더 빠를 수 있다. 이건 실제로 코드를 써봐야 안다.

## ADR-010: 배포 — 심사자는 어떻게 플레이하는가

### 상황
심사자가 게임을 어떻게 실행할지에 따라 아키텍처 전체가 달라진다. 아직 심사 환경이 확인되지 않았다.

### 가능한 시나리오

| 시나리오 | 대응 |
|---|---|
| **A. 제출된 URL로만 접속** | 서버를 어딘가에 배포해야 함. 무료 티어(Render, Railway 등) |
| **B. 로컬에서 직접 실행** | Docker Compose + README. 심사자 PC에 Docker가 있어야 함 |
| **C. 시연 영상으로만 평가** | 서버 배포 불필요. 영상 퀄리티가 전부 |
| **D. 현장에서 시연** | 우리 장비로 직접 보여주면 됨 |

### 결정
**A+B+C 모두 대비한다. 우선순위는 A > C > B.**

### 왜?

심사 환경을 통제할 수 없으므로 최대한 많은 경로를 열어둔다.

- **A (URL 접속)**: 가장 진입 장벽이 낮다. 무료 티어 서버에 올리되, AI 기능은 제한될 수 있으므로 Zero-Dependency Demo 모드가 여기서 작동해야 한다.
- **C (시연 영상)**: 어차피 제출물에 포함이다. Full Local AI 모드로 최고 품질 시연을 녹화한다.
- **B (로컬 실행)**: Docker Compose로 원커맨드 실행. README에 명확한 가이드. 하지만 심사자가 Docker를 설치할 가능성은 낮으므로 우선순위가 가장 낮다.

### 트레이드오프 인식
- 무료 서버 배포 시 AI 기능(Ollama 등)을 올릴 수 없을 수 있다. Demo 모드로 대응.
- 세 가지 경로를 다 준비하면 시간이 분산된다. 하지만 Demo 모드는 고정 데이터 + 규칙 기반이라 추가 공수가 크지 않다.
